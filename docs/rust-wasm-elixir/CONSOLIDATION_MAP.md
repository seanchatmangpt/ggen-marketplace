## 5. Conflicts between packs

1. **Two live "the WASM JSON ABI" claims — `wasi-json-abi-pack` vs `ex4pm-wasm4pm-bindings-pack`.** Different calling conventions for the same stated semantic (JSON request/response over linear memory): single-entry dispatch `gl_call/af_call(ptr,len) -> packed (out_ptr<<32)|out_len` vs per-algo exports `<algo>_v1(ptr, len, out_len_ptr)` + separate `alloc_v1/dealloc_v1/free_v1`. No byte conflict (disjoint prefixes/subjects) but the ecosystem now carries two incompatible host protocols; any host renderer (rank 3) must parameterize over the convention or the packs must record the failed-edge explicitly. Evidence: `~/graphlaw/wasm/src/lib.rs:9-18` vs `~/wasm4pm/docs/abi/ex4pm-bindings.md` "Calling convention" vs `~/ex4pm/lib/ex4pm_engine/wasm/real_transport.ex` moduledoc.
2. **`beam4pm-contracts-pack` v0.2.0 vs beam4pm's vendored pre-consolidation forks.** Marketplace consolidated `beam4pm-ai-contracts-pack` (v0.1.1) + `beam4pm-mcp-contracts-pack` (v0.1.0) into one pack; `~/beam4pm/ggen.toml` still wires BOTH forks from `vendor/ggen-marketplace/packs/` (versions confirmed on disk: 0.1.1 and 0.1.0). Until beam4pm migrates, two admission units exist for the same vocabulary — the exact cross-pack duplicate-facts topology that wasm4pm-breed-provenance-pack exists to catch, with no equivalent guard here.
3. **`beam4pm-wasm-engine-pack` (26.9.1, 72 ops, 4 engines) vs `ex4pm-wasm4pm-bindings-pack` (0.1.2, 33 algos + replay).** Both model "BEAM-hosted wasm engine wire surface" for sibling repos. Subjects are disjoint (beam4pm vs wasm4pm-ex4pm-bindings), but `beam4pm-wasm-engine-pack`'s reflection surface ("today has no counterpart to beam4pm_types_manifest") is the same semantic ex4pm solves with `algo_registry.ex` + the bindings pack. Not merged, not cross-referenced in either pack.toml.
