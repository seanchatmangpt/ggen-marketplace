# Experimental methods and benchmark protocol

## 1. Purpose

A research architecture becomes credible when another team can design an experiment that might disconfirm it. This chapter defines a preregisterable evaluation protocol for ggen Marketplace and compatible semantic-manufacturing systems.

The protocol is intentionally broader than “did CI pass?” It evaluates six claim families:

1. **correctness of manufacture**;
2. **replay and independent reproducibility**;
3. **failure localization**;
4. **semantic leverage and drift reduction**;
5. **operational throughput and WIP**;
6. **authority containment and evidence integrity**.

No single metric crowns the architecture. Results should be reported as a vector.

## 2. Experimental philosophy

The system makes both deterministic and empirical claims, and the evaluation method must respect the difference.

For a fixed byte-equivalence claim, one mismatch is enough to falsify reproducibility for that subject and environment class. Statistical significance is not required to explain away a deterministic mismatch.

For performance, maintenance effort, repair time, or defect-rate claims, repeated samples and uncertainty estimates are necessary.

For security claims, absence of observed escape is not proof of impossibility. The protocol therefore combines negative controls, capability inspection, and adversarial tests.

## 3. Unit of analysis

The primary unit is a **manufacturing episode**:

`E = (subject, environment, transition sequence, consequences, receipts)`.

A subject SHOULD bind at minimum:

- repository commit/tree;
- pack source digest;
- consumer semantic source digest;
- template/query identities;
- ggen/toolchain version;
- validator policy version;
- declared relevant environment.

An episode SHOULD record each transition independently:

`observe → admit → select → construct → verify → DO → receipt → standing`.

This avoids treating a workflow run as one opaque sample.

## 4. Experimental populations

Evaluation should use several populations rather than a single showcase pack.

### Population P1 — Minimal fixtures

Small synthetic consumers designed to isolate one semantic rule. These are useful for negative controls and fast regression.

### Population P2 — Representative marketplace packs

A stratified sample across semantic-only, projection, and project-style profiles; small and large pack source trees; different ontology and template complexity.

### Population P3 — Self-hosting infrastructure

Marketplace infrastructure generated by marketplace packs, such as the mdBook publication plane. This population exposes integration assumptions missing from toy fixtures.

### Population P4 — External real consumers

Repositories not developed solely to demonstrate the pack. This is the strongest test of genericity and documentation quality.

### Population P5 — Adversarial subjects

Intentionally malformed or hostile inputs designed to test admission, path containment, source non-mutation, authority boundaries, and refusal precision.

## 5. Baselines

A benchmark without a baseline can only report absolute behavior.

Recommended baselines are:

### B0 — Hand-maintained artifacts

A human maintains target files directly without semantic source or generation.

Measures maintenance effort and drift relative to a single-source projection.

### B1 — Conventional template projection

A deterministic template engine receives structured data but no graph/query layer, receipt model, or marketplace qualification.

Measures the incremental value of semantic selection and qualification over templating alone.

### B2 — Generator with unit tests only

The generator has local tests but no real-consumer qualification or exact-head publication court.

Measures the value of boundary execution.

### B3 — CI with mutable branch identity

A workflow validates the branch without asserting the exact subject SHA.

Used as a negative baseline for exact-subject evidence under concurrent commits.

### B4 — Probabilistic synthesis with post-hoc tests

A model or agent generates the same target class and relies on target tests after generation.

Measures flexibility, cost, repair time, and failure profile rather than assuming one paradigm dominates.

Baselines SHOULD be capability-matched enough that the comparison is meaningful.

## 6. Reproducibility ladder

The term “deterministic” is too coarse. Report the highest replay class passed.

### R0 — In-process repeat

Same process, same workspace, repeated manufacture.

Useful only for catching obvious stateful rendering defects.

### R1 — Fresh-process replay

New process, same workspace and machine.

### R2 — Fresh-workspace replay

Clean checkout/workspace on the same machine class.

### R3 — Fresh-runner replay

Independent ephemeral runner using the same declared OS/toolchain class.

### R4 — Cross-provider replay

Independent infrastructure provider or materially independent machine image using the same declared relevant inputs.

### R5 — Capsule reconstruction

A third party starts from a published release capsule containing source identities, build instructions, declared environment/toolchain identities, and expected artifact digests.

For byte-reproducible targets, each class passes only when all specified artifact digests match.

For semantic equivalence targets, the equivalence relation and canonicalization MUST be preregistered before execution.

## 7. Core outcome metrics

### 7.1 Manufacturing success rate

`MSR = successful admitted manufactures / admitted manufacture attempts`.

Report refusal separately; a correctly refused malformed subject is not a manufacturing failure.

### 7.2 Replay convergence rate

`RCR = subjects with equivalent replay / replayed subjects`.

Report by replay class R0–R5.

### 7.3 Drift incidence

`DI = unintended generated/source divergence events / observation period`.

For hand-maintained baselines, define semantically equivalent duplicated fields in advance.

### 7.4 Semantic leverage

One possible measure:

`SL = independently verified consequence fields / independently maintained semantic facts`.

A second, artifact-oriented measure:

`SL_A = target artifact classes / semantic source classes`.

Leverage without fidelity is not valuable, so report alongside defect rate.

### 7.5 Failure localization precision

For a seeded defect with known responsible boundary, measure whether the system's refusal/failure identifies:

- correct phase;
- correct subject;
- correct path/constraint;
- correct remedy class.

Define an ordinal score before the experiment rather than grading errors after seeing them.

### 7.6 Mean time to repair

`MTTR = repair-complete time - first admissible failure observation`.

Compare typed refusal versus generic failure where ethical and practical.

### 7.7 Evidence lead time

`ELT = full-standing timestamp - source-change timestamp`.

This is the evidence analogue of delivery lead time.

### 7.8 Receipt reuse rate

`RRR = reused valid proof obligations / total proof obligations`.

Report false-reuse incidents separately; an unsoundly reused receipt is more serious than low reuse.

### 7.9 Boundary escape rate

`BER = unauthorized consequential transitions / adversarial attempts`.

A zero observed rate is empirical evidence, not a proof of zero probability.

## 8. Little's Law and evidence queues

For a stable system, Little's Law gives:

`L = λW`

where:

- `L` is average WIP;
- `λ` is throughput;
- `W` is average lead time.

For semantic manufacture, maintain at least three queues separately:

- **construction WIP** — candidates not yet manufactured;
- **evidence WIP** — manufactured subjects awaiting required validation;
- **actuation WIP** — validated subjects awaiting authorized `DO`.

Collapsing these queues hides the actual bottleneck. At high generation throughput, evidence WIP is expected to dominate unless qualification scales similarly.

The benchmark should therefore report:

`L_construct`, `L_evidence`, `L_DO`

and corresponding lead times.

## 9. Experimental perturbations

A reproducibility experiment is more informative when it varies factors known to induce hidden state.

Recommended perturbations include:

- filesystem checkout path;
- locale;
- timezone;
- file enumeration order where controllable;
- clean versus warm cache;
- runner image within declared compatibility class;
- CPU count;
- concurrency level;
- network disabled where manufacture claims no network need;
- environment variable noise;
- unrelated files present in workspace;
- dependency cache order.

The experiment must distinguish **declared irrelevant perturbations** from changes that legitimately alter the subject.

## 10. Negative-control suite

Negative controls establish that the court can detect invalidity rather than merely producing green output.

### NC-01 — Exact-head mismatch

Execute a different commit than the claimed subject.

Expected: typed refusal before qualification.

### NC-02 — Pack source mutation

A template or gate writes into its own pack source subtree.

Expected: qualification failure with mutation evidence.

### NC-03 — Nondeterministic timestamp

Inject wall-clock time into a generated artifact.

Expected: replay mismatch.

### NC-04 — Unordered semantic projection

Remove ordering from a query whose result order controls output.

Expected: dedicated admission refusal or instability under perturbation.

### NC-05 — Output path collision

Compose two packs that write the same path without a merge operator.

Expected: composition refusal before manufacture.

### NC-06 — Missing graph cardinality

Create a chapter without the required path.

Expected: graph/admission refusal or target-compiler failure, with earlier detection preferred.

### NC-07 — Path traversal

Provide a target path outside the consumer root.

Expected: refusal; no filesystem escape.

### NC-08 — Unauthorized deployment

Attempt Pages or equivalent publication from a qualification-only context.

Expected: unavailable capability or explicit authority refusal.

### NC-09 — Stale receipt reuse

Change a validator/toolchain dependency and attempt to reuse an older receipt without an equivalence proof.

Expected: receipt invalidation.

### NC-10 — Hand-edited generated consequence

Modify committed generated metadata while leaving semantic source unchanged.

Expected: regeneration/drift court identifies the difference.

A release should not claim strong validator standing if the corresponding negative controls are never exercised.

## 11. Failure-injection taxonomy

Seed faults at each layer:

| Layer | Example fault | Expected court |
|---|---|---|
| observation | malformed config input | parser/admission |
| semantic graph | missing required relation | SHACL/native gate |
| query | wrong variable/order | qualification/replay |
| template | invalid syntax | ggen/template compiler |
| target artifact | invalid TOML/code | target compiler |
| filesystem | source mutation/path escape | qualification sandbox |
| subject identity | checkout mismatch | exact-head gate |
| authority | forbidden token/action | capability/policy boundary |
| publication | bad Pages config | deployment court |
| receipt | stale/mismatched predecessor | standing derivation |

Localization quality should be measured against the seeded layer.

## 12. Statistical analysis

### Binary outcomes

For success/failure proportions, report counts plus a confidence interval such as Wilson interval. Do not report only percentages for small samples.

### Latency and cost

CI and build times are usually skewed. Report median, interquartile range, and tail percentiles. Bootstrap confidence intervals are preferable to assuming normality without evidence.

### Repair experiments

For paired defects tested under two diagnostic regimes, use paired analysis where possible. Record operator experience because repair-time comparisons are strongly confounded by familiarity.

### Deterministic equality

For exact artifacts, the primary statistic is equality itself. Report the number of independent replays and perturbation classes so readers can judge environmental coverage.

### Multiple packs

Do not pool fundamentally different pack profiles without stratification. A semantic-only pack and a project-scale pack have different opportunity for failure and different latency distributions.

## 13. Cost accounting

High-throughput manufacture can shift cost rather than remove it. Track:

- CPU seconds;
- runner minutes;
- network bytes where relevant;
- artifact storage;
- validation fan-out;
- human repair minutes;
- review minutes;
- repeated work caused by stale or invalidated receipts.

Define evidence efficiency:

`EE = validated consequential value / evidence cost`.

The numerator must be operationalized for each study; it cannot be a vague productivity score.

## 14. Semantic-maintenance study

To test the source-singularity hypothesis, create equivalent changes across baseline systems.

Example change family:

“Rename one domain concept and add one field that must appear in CLI help, API schema, documentation, validation, and telemetry.”

For each system measure:

- number of authoritative edits;
- number of generated edits;
- inconsistent intermediate states;
- total change lead time;
- defects escaping the validation court;
- reviewer effort.

This directly tests whether ontology-first manufacture reduces coordination work rather than merely moving text into Turtle.

## 15. Composition study

Construct pack pairs across four classes:

1. disjoint graph + disjoint targets;
2. shared graph + disjoint targets;
3. compatible shared targets with explicit merge operator;
4. conflicting targets or authority.

Test whether the composition court:

- accepts the first three when lawful;
- refuses the fourth before side effects;
- preserves deterministic replay;
- invalidates only the required receipt closure when one pack changes.

This study evaluates the pack algebra rather than isolated pack quality.

## 16. Authority-containment study

Create a capability matrix with rows as phases and columns as capabilities:

| Phase | repository read | workspace write | network read | secret read | remote write | deploy |
|---|---:|---:|---:|---:|---:|---:|
| SELECT | expected | no/limited | policy | no | no | no |
| CONSTRUCT | expected | bounded | policy | no by default | no | no |
| VERIFY | expected | bounded | policy | only validator-specific | no by default | no |
| DO | expected | bounded | policy | explicit | explicit | explicit |

Attempt seeded transitions that violate each denied cell. The study reports actual enforcement, not intended policy.

## 17. Evidence-integrity study

Test whether standing derivation fails closed when:

- a predecessor receipt is absent;
- a subject digest changes;
- the validator version changes;
- the receipt timestamp is outside policy validity;
- an authority witness is missing;
- two required boundaries executed different source trees;
- a receipt claims an output whose digest does not match the artifact.

This is necessary before receipt reuse can safely reduce CI work.

## 18. Replication package

Every published benchmark SHOULD include:

- exact repository commit/tree identities;
- pack and consumer source fingerprints;
- admitted configuration;
- toolchain versions and acquisition method;
- commands/workflow definitions;
- relevant environment description;
- raw receipt/event data;
- expected artifacts and digests;
- negative-control definitions;
- analysis script or notebook;
- explicit exclusions and failed runs.

A replication package is not complete if a third party must infer which failures were discarded.

## 19. Preregistration template

Before a consequential benchmark, record:

### Claim

What exact architecture claim is being tested?

### Subject population

Which packs/consumers are included and why?

### Baseline

What comparison system is used?

### Independent variables

Which architecture or environment factors vary?

### Outcomes

Which metrics are primary versus exploratory?

### Equivalence relation

What constitutes “same output”?

### Exclusion criteria

When is a run invalid rather than failed?

### Failure policy

How will partial success and boundary-local failure be recorded?

### Analysis

Which summary statistics/tests will be used?

### Falsifier

What result would count against the hypothesis?

This prevents post-hoc metric selection from turning every outcome into support.

## 20. Minimal benchmark suite for every release

A marketplace release aspiring to research-grade evidence should eventually execute at least:

1. corpus structural validation;
2. deterministic catalog/archive reconstruction;
3. real-ggen qualification for every admitted pack or proven affected closure;
4. replay comparison;
5. source non-mutation check;
6. exact-subject assertion;
7. representative negative controls;
8. self-hosted consumer build;
9. release-capsule generation;
10. independent or periodically scheduled higher-class reproducibility run.

Not every check must block every commit. The evidence policy may tier them by cost and risk. But a claim of broad release standing should make the missing tiers visible.

## 21. Reporting format

A benchmark report should end with a claim matrix rather than a single verdict.

| Claim | Subject | Boundary | Evidence | Result | Standing |
|---|---|---|---|---|---|
| pack loads | exact pack digest | ggen load | run receipt | pass | ALIVE |
| replay converges | same subject | R2 replay | digest pair | pass | ALIVE |
| target compiles | exact generated tree | target compiler | compiler receipt | pass | ALIVE |
| deployment works | exact artifact | remote Pages | deployment receipt | not run | UNKNOWN/BLOCKED |
| cross-provider reproducibility | release capsule | R4 | none | not run | UNKNOWN |

This table prevents successful lower boundaries from inflating higher claims.

## 22. From benchmark to science

The decisive upgrade is methodological:

> The marketplace should not optimize only for more packs, more commits, or more generated files. It should optimize for **higher semantic leverage at lower evidence lead time, with stable replay, precise refusals, bounded authority, and independently reproducible consequences**.

Those quantities can be measured. Once measured longitudinally, the architecture becomes comparable to alternatives and the research program becomes cumulative rather than anecdotal.
