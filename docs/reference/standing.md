# Reference: standing

Standing is a scoped claim about observed evidence for an exact subject and boundary. It is not a repository adjective that automatically transfers to every pack, consumer, environment, or external system.

## States

- `UNKNOWN` — the required boundary has not been observed with sufficient evidence.
- `PARTIAL_ALIVE` — one or more required courts succeeded, but the claimed closure is incomplete or requalifying.
- `ALIVE` — the exact admitted subject executed successfully across the exact boundary being claimed, with required evidence complete for that scope.
- `BLOCKED:<reason>` — execution cannot currently reach the required boundary because of a typed external/authority/transport/tooling blocker.
- `BUILD_BROKEN` — a real attempted build/verification boundary failed for the subject.
- `UNSUPPORTED` — the implementation/contract does not support the requested capability/boundary.
- `REFUSED:<reason>` — admission deliberately rejected the subject before the claimed transition.

`UNKNOWN != REFUSED`, `UNSUPPORTED != REFUSED`, and a checkpoint on one boundary is not a crown over another.

## Exact-subject law

Standing must bind the exact repository/head/tree/pack/consumer/configuration/toolchain/environment identities required by the claim. Historical success may only be reused when the relevant identities are proven equivalent.

A queued workflow, authored test, generated file, draft PR, workflow definition, or status badge does not establish ALIVE.

## Marketplace repository standing

A successful exact-subject marketplace court may establish structural source admission, deterministic catalog projection, source fingerprinting, path safety, all-pack ggen manufacture/replay, vacuity, Pages manufacture, or other explicitly executed repository gates.

Each result retains its own boundary. A red aggregate workflow caused by an independent repository-wide guard does not automatically refute a separately green pack-specific court; conversely, a green subjob cannot silently erase a real owning failure.

## Pack standing

A pack may have separate standing for:

- marketplace admission;
- ggen manufacture/replay;
- generated documentation correspondence;
- native consumer/runtime behavior;
- external integration;
- consequential actuation.

State the narrowest true claim.

## Level-5 standing

Level 5 is closure over the dimensions/boundaries named by [the Level-5 maturity contract](level5-maturity-contract.md). A pack cannot inherit L5 because `pack-maturity-pack` generated four documents or because marketplace qualification succeeded.

A defensible Level-5 claim must bind:

- authoritative semantic source;
- fail-closed admission/negative witnesses for the claimed domain;
- deterministic manufacture;
- exact-subject execution at the claimed consumer/runtime boundary;
- receipt/replay;
- authority fencing;
- composition/class closure;
- Tutorial + How-to + Reference + Explanation correspondence.

If one required exact-head court is still executing, use `PARTIAL_ALIVE / REQUALIFYING` rather than pre-promoting the result.

## Authority ceiling

Standing never grants authority beyond the court that produced it. A successful documentation, simulation, plan, or construction court cannot create external DO authority. Consequential actuation requires the responsible runtime's separately admitted authority path and receipt.

## Evidence invalidation

Standing must be reconsidered when any identity relevant to the claim changes: semantic source, validator, toolchain, configuration, dependency, environment, generated contract, consumer, authority policy, or exact code subject.

A change outside the claimed dependency closure may be classified as adjacent only after proving that separation; adjacency is not assumed from intuition.
