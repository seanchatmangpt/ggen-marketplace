# kubernetes-workload-pack

Schema-only vocabulary for rendering real Kubernetes Deployment + Service
YAML from typed `k8s:Workload`/`k8s:Container` facts -- built directly on
`github-actions-pack`'s proven shape (self-contained `to:`/`sparql:`/
`for_each:` template format, per-file `GENERATED by ggen. Do not edit.`
provenance, real SPARQL refusal gates instead of post-hoc lint).

Ships **zero individuals** (dspy-pack contract): a consumer admits its own
`k8s:Workload`/`k8s:Container` facts in its own `.ttl`, wires this pack in
their `ggen.toml`'s `[packs]` table, and gets a real, gate-checked
`k8s/<fileName>` rendered from those facts.

## Why this exists

Built in a session that live-hardened `~/xaas`'s hand-written `k8s/`
manifests against a real `kind-xaas` cluster (RBAC scoping, NetworkPolicy
default-deny enforcement, ResourceQuota enforcement, etcd-at-rest
encryption, pod/container `securityContext`) and found: no existing
marketplace pack rendered raw workload YAML at all (checked
`autofde-k8s-fault-taxonomy-pack`, `dfcm-full-deployment-pack`,
`fortune5-deployment-blocks-pack` -- all DFCM/Lean/catalog-shaped, none
of them a `kubectl apply`-able manifest). Rather than leaving the
just-hardened shape hand-authored (and therefore re-driftable the next
time someone edits it without re-deriving the same hardening), it became
real, reusable manufacturing capital here.

## Real gate: `gates/010_required.rq`

Refuses a `k8s:Workload` with no `k8s:podSecurityContextBlock` bound, or a
`k8s:Container` with no `k8s:resourceRequestsBlock`/`k8s:resourceLimitsBlock`
-- both are real, empirically-found gaps this session closed by hand
before this pack existed (0 of 3 workloads on the pre-hardening `xaas`
cluster set a `securityContext`; a `512Mi` memory limit OOM-killed a real
migration mid-run before being raised).
