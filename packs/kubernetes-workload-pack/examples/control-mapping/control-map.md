# control-mapping

Machine-readable-adjacent control map for `examples/high-assurance-workload/`.
Built from a Tier 1-4 authoritative-source research pass (NIST SP 800-53
Rev.5, SP 800-190, Kubernetes upstream Pod Security Standards / RBAC good
practices / application security checklist, CISA/NSA Kubernetes Hardening
Guidance, CIS Kubernetes Benchmark) -- identifiers and requirement
paraphrase only, no benchmark text reproduced verbatim.

**Terminology**: this pack is **NIST-control-mapped** and produces
**control implementation evidence** for the layer stated in each row. It
does not claim NIST certification, FedRAMP authorization, FIPS validation,
or STIG compliance -- those are organization/assessor/system-boundary
determinations NIST SP 800-53A's assessment procedures require a real
assessor to make, not a property a Kubernetes manifest can establish on
its own.

## Assessment boundary (read this before any row below)

| Layer | This pack's scope |
|---|---|
| `WORKLOAD_CONTROL` | Fields this pack's `ggen sync run` actually renders into the Deployment/Service YAML. Verifiable by reading the generated file. |
| `NAMESPACE_CONTROL` | RBAC Role/RoleBinding, ResourceQuota/LimitRange, NetworkPolicy objects. Not yet generated by this pack (v0.1.0 disclosed backlog, `pack.toml`) -- **INHERITED**, assumed provided by the consumer's own namespace manifests. |
| `CLUSTER_CONTROL` | Pod Security Admission enforcement mode, CNI NetworkPolicy enforcement, admission-controller policy (Kyverno/Gatekeeper), audit logging, etcd-at-rest encryption. **INHERITED** -- the cluster operator's responsibility; a workload manifest cannot force a cluster to enforce anything. |
| `NODE_CONTROL` | kubelet/API-server/etcd file permissions and flags (CIS Kubernetes Benchmark master/node sections). **INHERITED**, and for a managed Kubernetes offering, owned by the cloud provider, not expressible from any workload or namespace object. |
| `SUPPLY_CHAIN_CONTROL` | SBOM, image signing/provenance (Sigstore/cosign), vulnerability scanning, base-image lifecycle. **INHERITED** from the consumer's CI/build pipeline -- out of this pack's Kubernetes-manifest scope; represented here as evidence *expectations*, not enforced fields. |
| `ORGANIZATIONAL_CONTROL` | Secret rotation policy, incident response, personnel/process controls (NIST SP 800-53 PS/IR/CA families). **INHERITED**, organizational-process scope entirely outside any generated artifact. |

## Orthogonal scanner layer (real, run this session)

`qualification/orthogonal_scan.sh` renders every positive fixture and both
known-gap negative controls for real, then runs four independent sensors
that never see this pack's own SPARQL gate:

| Tool | What it proves | Real result this session |
|---|---|---|
| `kubeconform -strict` | Generated objects conform to the pinned Kubernetes OpenAPI schema | All 8 rendered resources across 7 fixtures: **valid**, 0 invalid, 0 errors |
| `trivy config --severity HIGH,CRITICAL` | Misconfiguration scan independent of Kubernetes admission | `privileged-container-KNOWN_GAP` fires `AVD-KSV-0017` (privileged) + `AVD-KSV-0014` (readOnlyRootFilesystem); `mutable-image-tag-KNOWN_GAP` fires `AVD-KSV-0014`; `high-assurance-workload`: 0 findings |
| `kyverno apply` (`qualification/policies/restricted-pss-subset.kyverno.yaml`) | Policy-engine admission simulation, expected-pass/expected-fail testing | 16 pass / 8 fail across 8 resources -- both known-gap fixtures fail every relevant rule; `xaas-workload` (not claimed high-assurance) fails only the digest rule, as expected; `high-assurance-workload` passes all 4 |
| `kubescape scan framework NSA,cis-v1.10.0` | Independent NSA/CIS-aligned control assessment (not a Trivy/Kyverno restatement) | 79% aggregate compliance across 6 fixture Deployments; `Privileged container` and `Insecure capabilities` controls correctly fail only the privileged fixture; `high-assurance-workload` fails only `Ingress and Egress blocked` (NetworkPolicy -- correctly out of this pack's v0.1.0 scope, see SEC-NET-001) and `Apply Security Context` (a Kubescape-specific stricter subcheck not yet reconciled against this pack's own securityContext fields -- open follow-up, not investigated further this pass) |

Cosign is deliberately **not** wired into this script -- see SEC-COSIGN-001.

**Scope decision, made deliberately rather than by adding every available
tool**: `kube-bench` was not added as a PR gate against a local `kind`
cluster, because `kind`'s containerized control-plane/node configuration
is not representative of the production managed-cluster substrate this
pack's consumers actually run on -- a `kube-bench` pass against `kind`
would be evidence about `kind`, not about the workload. Grype/Syft were
not added alongside Trivy (which already covers image vulnerabilities and
SBOM generation) to avoid two tools answering the same question with no
independent falsifier. Checkov was not added alongside Kyverno + Trivy
config + Kubescape, which already cover this pack's generated-manifest
surface from three genuinely different angles (policy engine, static
misconfiguration, NSA/CIS framework assessment). OpenSSF Scorecard and
Falco are correctly out of a single pack's scope entirely -- Scorecard is
a repository-wide supply-chain hygiene signal (candidate for a
main/nightly job, not a per-pack PR gate) and Falco answers a runtime
threat-detection question this pack's generate-time scope cannot address.

## Standing summary

`ALIVE` = enforced by gate 010 or directly readable in the generated YAML,
today, in this repository. `PARTIAL_ALIVE` = the property's *presence* is
enforced but its *value* is not. `BLOCKED` = named, candidate, not yet
built. `INHERITED` = correctly out of scope for a workload manifest;
listed so a future engineer never has to rediscover the boundary from
first principles (the explicit BFCC-E requirement this map exists to
satisfy).

## Live cluster verification (real `kind`, this session)

A real `kind` cluster (`k8s-pack-live`) was created, a namespace labeled
`pod-security.kubernetes.io/enforce=restricted`, and a `ResourceQuota`
(`requests.cpu=1, requests.memory=1Gi`) applied, then every example and
the `privileged-container-KNOWN_GAP`/`legitimate-exception` fixtures were
rendered for real and `kubectl apply --dry-run=server`'d against it.
Cluster deleted afterward; repo left clean (`git status --short` empty).

| Check | Real result |
|---|---|
| `minimal-secure-workload`, `high-assurance-workload` | Both **admitted cleanly**, zero PodSecurity warnings, in a namespace with `restricted` enforced. |
| `high-assurance-workload` at 3 replicas x 250m CPU request (750m total) against a 1-CPU quota | **Admitted** -- correctly within quota. |
| A bare Pod requesting `cpu: "2"` against the same 1-CPU quota | **Rejected**: `Error from server (Forbidden): ... exceeded quota: demo-quota, requested: requests.cpu=2, used: requests.cpu=0, limited: requests.cpu=1`. ResourceQuota enforcement is real. |
| `negative-controls/privileged-container-KNOWN_GAP` (`privileged: true`) applied as a **Deployment** in a namespace with PSA `enforce=restricted` | **Not rejected** -- `kubectl` printed the full PodSecurity violation list (`privileged`, `allowPrivilegeEscalation`, unrestricted capabilities, `runAsNonRoot`, missing `seccompProfile`) as a **warning only**, and still reported `deployment.apps/privileged-demo created (server dry run)`. |
| Same fixture applied as a **bare Pod** instead of via a Deployment wrapper | Would be hard-rejected by PSA at admission (not independently re-run here, but this is Kubernetes' documented behavior and the mechanism the row below names). |

**Important corrected finding, not assumed going in**: Kubernetes' Pod
Security Admission controller validates pod *templates* inside workload
resources (Deployment/ReplicaSet/StatefulSet/etc.) but, per upstream
design, only **warns** at that object's own admission -- it cannot reject
the Deployment itself, because the Deployment controller (not the
apiserver request in front of you) is what actually creates the Pod
object later, and *that* creation is where `enforce=restricted` would
produce a real rejection. `kubectl apply --dry-run=server -f
deployment.yaml` therefore is **not sufficient evidence** that a
Deployment's pod spec would survive a live restricted namespace -- only a
bare Pod apply, or watching the ReplicaSet's real Pod-creation events, is.
This pack's generated artifact is always a Deployment (never a bare Pod),
so `SEC-PRIV-001`'s live consequence is: the object-level `kubectl apply`
this pack's own docs recommend for schema validation will **not** surface
a live PSA rejection for a privileged container -- only a full live
rollout (watching for the ReplicaSet's Pod to actually fail admission)
would. `SEC-PRIV-001` remains `BLOCKED` (unfixed by this finding) and is
updated to *additionally* flag this `kubectl apply --dry-run=server`
limitation so a future engineer doesn't mistake a clean dry-run for a
verified-safe privileged workload.
